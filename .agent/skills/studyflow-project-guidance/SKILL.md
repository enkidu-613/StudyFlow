# StudyFlow 项目指导

让用户能够理解、执行并验证 StudyFlow 的每一步。任何方案都必须回答：改什么、在哪执行、值从哪里来、成功长什么样、失败如何定位、是否可以回滚。

## 开始前读取上下文

先读取：

- `.agent/AGENTS.md` 和本文件。
- 当前计划、根目录 `README.md`、相关模块 README、`mise.toml`。
- 实际的 `server/`、`apps/client/`、`infra/` 文件和 `.env.example`。
- `git status --short`，区分用户已有修改、计划中的修改和本次修改。

不要把计划书当成已部署事实；先用文件、命令输出或日志确认当前状态。不要假设仍在使用 Supabase、某个数据库、某个域名或某个认证流程。

## 方案与实施契约

对每个阶段使用 [友好计划与部署模板](references/user-friendly-output-template.md)，至少写出：

1. 目标和完成后的可见结果。
2. 当前证据、前置条件和技术取舍。
3. 修改的文件及其职责。
4. 每条命令的执行位置：`本机 Mac`、`VPS`、`项目根目录`、`客户端目录`或`服务器目录`。
5. 可直接复制的命令、预期输出和验证命令。
6. 常见失败原因、对应日志和安全的回滚动作。
7. 阶段完成检查点；未通过检查点时不要静默进入下一阶段。

先完成一个最小可运行切片，再扩展功能。涉及数据库迁移、权限、防火墙、证书、删除数据或覆盖部署时，先写安全边界、备份和回滚路径；得到用户授权后再执行破坏性动作。

## 配置、账户与密钥

每个环境变量必须进入“变量说明表”，列出：变量名、作用、谁生成或提供、准确获取位置、填写示例、作用范围、是否敏感、验证方式。禁止只写 `[YOUR-PASSWORD]`、`填你的 token` 或一串没有来源的常量。

- 生成的服务端密钥使用明确命令，例如在 VPS 执行 `openssl rand -hex 32`，说明结果写入哪个 `.env` 项、只由哪个服务读取。
- 用户提供的 AI `BASE_URL`、模型名和 API key 说明“客户端设置页 → AI 设置”的具体字段；除非架构明确要求，否则不要塞进服务端 `.env`。
- 邮箱注册密码由用户在注册页创建；说明服务端如何哈希、数据库存什么、登录请求经过哪条链路。不要把普通登录密码当作 VPS 密码、数据库密码或 JWT 密钥。
- SSH、数据库、JWT、第三方 API key、恢复密钥分别解释来源和用途，不能混称为“token”。
- `.env`、私钥、恢复密钥和真实 IP 不写入 Git、计划书、截图或最终示例；使用 `api.example.com`、`<VPS_PUBLIC_IP>` 和 `<REDACTED>`。
- 数据库 URL 中的特殊字符必须说明 URL 编码规则；不要把未经编码的密码直接拼进连接串。
- 缺少真正需要用户提供的秘密时，只指出准确的文件、变量名、获取页面或生成命令；不要猜测，也不要索取已经可以在仓库或服务器上检查到的内容。

## 难点升级与查错策略

遇到无法自行解决的难点或报错时，按以下顺序升级，不要卡住不动：

1. **先自查**：查阅相关技术的官方文档和风评良好的编程论坛/问答社区（如官方 docs、Stack Overflow、GitHub Issues、flutter.dev、FastAPI/SQLAlchemy 官方文档），用搜索关键词定位问题。把查到的官方结论作为方案依据。
2. **子代理升级序列**：仍然无法解决时，依次启动子代理：
   - 后端 API/数据模型/迁移/接口契约问题：第一优先 `后端设计` 子代理（设计方案与验收），由 `后端执行` 实现。
   - 部署/容器/网络/数据库/生产事故：第一优先 `运维设计` 子代理（设计方案与验收），由 `运维执行` 执行。
   - 测试策略/用例/覆盖率/测试失败归因：第一优先 `测试设计` 子代理（设计用例与验收），由 `测试执行` 编写与运行。
   - 仍然不行：`架构排障` 子代理。
   - 最终手段：`界面规划` 子代理。
3. **子代理推理强度梯度**：子代理按“推理强度从低到高”逐级提升——先用低推理强度的模型快速尝试，解决不了再换更高推理强度的模型，避免一开始就用昂贵/慢的模型，也不要长时间卡在低强度模型上：
   - 低强度：`前端实现`（快速试错、简单改动）、`后端执行`（按契约实现代码）、`运维执行`（按方案执行命令、收集证据）、`测试执行`（按用例编写与运行测试）。
   - 中强度：`重构工程师`（中等复杂度推理与重构）、`后端设计`（API/数据模型方案设计与验收）、`运维设计`（部署/排障方案设计与验收）、`测试设计`（测试策略与用例设计、验收）。
   - 高强度：`架构排障`、`前端修复`、`界面规划`（复杂架构、疑难排障、界面设计规划）。
   - 记录每一级：尝试了什么、结果如何、为什么放弃，供下一级参考。
4. 使用子代理时，把已尝试的命令、报错原文、相关文件路径和已查阅的官方文档一并交给它，避免重复劳动。
5. 每个升级层级都要记录：尝试了什么、结果如何、为什么放弃该方案，供下一层代理参考。

### 子代理调度模式（融合自 multi-agent-orchestration）

调度子代理前，先判断任务依赖关系，再选模式，避免一律串行等待：

- **顺序链**：任务有依赖（前一步输出是后一步输入）时用。例如 `界面规划` → `前端实现` → `设计验收`，每一步交接时把前一步的产出（规划文档、实现记录）显式传给下一步。
- **并行执行**：多个独立任务同时推进时用，显著提速。例如：界面改造（`前端实现`）与接口契约核对（`设计验收`）互不依赖，可同时启动，再合并结果。要求：任务间无共享可变状态、交接内容互不依赖。
- **层级协调**：主代理作为协调者，把任务拆成多个可并行的子任务分派给不同子代理，再统一汇总验收；大型改动用"先规划（`界面规划`）→ 并行实现（`前端实现` 多路）→ 汇总验收（`设计验收`）"。
- **双通道复核**：高风险决策（数据库迁移、认证改造、破坏性操作）用两个子代理独立分析再对照，例如 `架构排障` 出方案 + `设计验收` 独立审查，或 `运维设计` 出部署方案 + `设计验收` 审查回滚路径，避免单一视角盲点。
- **运维设计与执行分工**：部署/运维任务按"设计 → 执行 → 验收"分工——`运维设计` 出流程与方案（含预期输出、验证命令、回滚路径）→ `运维执行` 逐条执行并带回证据 → `运维设计` 验收；出现问题由 `运维设计` 出解决方案、`运维执行` 执行。
- **后端设计与执行分工**：后端任务按"设计 → 实现 → 验收"分工——`后端设计` 出接口契约与数据模型方案（含迁移与回滚）→ `后端执行` 实现端点/模型/迁移/测试并带回 pytest 与 lint 结果 → `后端设计` 六维验收；契约冲突或实现分歧由 `后端执行` 上报、`后端设计` 定夺，`后端执行` 不自行改契约。
- **测试设计与执行分工**：测试任务按"设计 → 编写运行 → 验收"分工——`测试设计` 出测试策略与用例方案（金字塔分层、风险导向、性能预算）→ `测试执行` 编写 pytest/widget 测试并运行、带回覆盖率与失败堆栈 → `测试设计` 六维验收；测试失败由 `测试执行` 归因（产品缺陷 vs 用例缺陷）上报，`测试设计` 定夺修复方向。
- **交接契约**：每次派发子代理必须携带——目标与成功标准、已尝试记录、相关文件路径、报错原文/日志、截止边界（何时升级下一级）。子代理返回时带回——结论、改动清单、验证结果、剩余风险，供下一环节直接消费。
- **失败回退**：每个子任务预设回退路径：该子代理失败 → 下一强度子代理接手其完整记录 → 仍失败 → 换更高强度/换模式（串行改并行、双通道改共识）。不让任何一级静默卡死。

## 前端界面规划与执行分工

- **前端界面规划**：由 `界面规划` 子代理负责界面与交互设计，输出页面结构、状态流转和组件拆分方案。
- **前端实现执行**：由 `前端实现` 负责落地规划，编写 Flutter 界面与状态代码。
- **实现出现问题时**：先由 `前端修复` 和 `架构排障` 子代理依次修改修复。
- **再往后**：按同样的“规划 → 执行 → 修复”分工逐级轮换，直到问题解决；每级都要记录尝试与结果，避免重复劳动。
- **推理强度从低到高**：先让低推理强度模型（`前端实现`）快速落地，遇阻再升到中（`重构工程师`）、高（`前端修复`、`架构排障`、`界面规划`）强度模型处理复杂设计与疑难问题，避免一上来就用高成本模型。
- **并行派发**：多个页面/组件互不依赖时，可同时启动多个 `前端实现` 任务并行落地，主代理负责汇总；并行任务各自独立目录与改动范围，避免文件冲突。
- **规划先行**：多页面改动必须先由 `界面规划` 输出统一的设计 token 与组件拆分，再并行实现，保证视觉一致。
- 界面与交互设计必须优先考虑用户使用友好性：清晰的状态提示、可逆操作、空态/错误态/加载态覆盖、合理的默认值与输入校验。

## 借鉴优秀开源项目

- 项目代码设计优先参考 GitHub 上相似业务、同技术栈且口碑良好的开源项目（如 Flutter 任务管理、日历、专注/番茄钟、离线同步类应用），借鉴其目录结构、命名、状态管理、本地存储和同步模式。
- 借鉴只取其设计理念与模式，不照抄协议、专有资产或违反许可证的代码；在 README 或设计文档中记录借鉴来源与边界，保持本项目许可证合规。

## 部署与排障

部署文档按“本机准备 → 推送 → VPS 登录 → 备份 → 安装/更新 → 写入 `.env` → 启动 → 迁移 → 健康检查 → 注册登录 → 同步 → AI → 备份恢复验证”排列。每一步都标注当前用户和目录。

同时检查云厂商安全组和 VPS 内防火墙；解释 22、80、443 或应用内部端口各自的用途，应用容器端口默认不直接暴露公网。兼容 `docker compose` 与旧版 `docker-compose` 时，先检测实际可用命令再给对应写法。

排障先收集证据，再改配置，按 DNS → TCP 端口 → TLS/Cloudflare → Caddy/反向代理 → API → 数据库 → 认证的边界逐层定位。看到 Cloudflare 525 时解释为边缘到源站 TLS 握手失败，分别检查源站监听、证书、代理模式和日志；不要把关闭代理、关闭防火墙或关闭用户网络代理当作默认修复。

## 交付标准

完成前必须实际运行与风险相称的测试、配置校验、健康检查和关键用户流程。最终报告用中文，先给结论，再列：已改文件、用户需要填写的最少项目、每项来源、验证结果、剩余风险和下一步。没有新证据就不要声称“已完成”“已部署”或“已修复”。
